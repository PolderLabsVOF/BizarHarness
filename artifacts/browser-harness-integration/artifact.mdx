# Feature: Browser-harness integration

**Status:** `[STATUS:shipped]` · **Author:** `drb0rk` · **Created:** `2026-06-26T11:30:00.000Z`

> [INFO]
> v3.20.7 integrates https://github.com/browser-use/browser-harness
> (v0.1.3, June 21 2026) as the **primary browser-driven E2E tool**
> for the `browser-harness` Bizar agent. Replaces the previous
> agent-browser MCP fallback with a stable, Python-via-uv tool that
> survives shell exit and uses the chrome-headless-shell binary
> (which works around the Arch Linux crashpad bug).

## Why browser-harness (the Python tool), not agent-browser MCP?

| Option | Pros | Cons |
|--------|------|------|
| A: agent-browser MCP (opencode built-in) | Zero install | Requires opencode to spawn Chrome with the right flags; ties the agent to a specific opencode version; the MCP tool surface is a subset of what browser-harness offers |
| B: **browser-harness (browser-use/browser-harness)** | Thin CDP harness; ~1k LOC; actively maintained (15.4k stars, 1.4k forks); works in any shell context; can drive local Chrome or Browser Use Cloud browsers | One more dep to install (Python 3.12 + uv + ~12 packages) |

We chose **Option B** because:

- The user's machine has a known crashpad issue with system chromium
  (the handoff flagged this). chrome-headless-shell avoids crashpad
  entirely.
- The Python tool is invoked via `bash` heredoc, which is the most
  portable way to run from any agent context (opencode, raw opencode
  run, human terminal).
- browser-harness surfaces more CDP primitives than the agent-browser
  MCP (`js()`, raw `cdp("Domain.method", ...)`, file upload via
  `upload_files()`, print-as-pdf, profile cookie sync for cloud
  browsers).
- It supports local Chrome via DevToolsActivePort (no Browser Use
  Cloud required for basic flows) and Browser Use Cloud for
  headless / parallel sub-agent cases.

## Install

### For users (one-shot)

```bash
uv tool install --python 3.12 --upgrade --force browser-harness
mkdir -p ~/.opencode/skills/browser-harness
browser-harness skill > ~/.opencode/skills/browser-harness/SKILL.md
cli/browser-harness-up.sh start    # or: bizar browser-harness-up start
```

After this, `browser-harness --doctor` reports:

```
browser-harness doctor
  platform          Linux ...
  python            3.12.13
  version           0.1.3 (pypi)
  latest release    0.1.3
  [ok  ] chrome running
  [ok  ] daemon alive
  [FAIL] active browser connections — 0          # normal, no active session
  [FAIL] Browser Use cloud auth — optional        # skip for local-only
```

### For the BizarHarness installer

`install.sh` now includes an optional browser-harness install block.
If `uv` and `python3.12` are on PATH, it auto-installs and registers
the skill. Otherwise it logs a warning telling the user to run the
one-shot commands above.

## Chrome startup helper

`cli/browser-harness-up.sh` is a small wrapper that:

1. Picks the best available chrome binary (prefers chrome-headless-shell
   from the puppeteer cache, then system chromium / google-chrome).
2. Launches chrome with `--headless --remote-debugging-port=9222
   --user-data-dir=~/.config/chromium`.
3. Waits for the CDP port to come up.
4. Survives parent shell exit via `setsid + nohup + disown` (the
   Bizar background-process footgun documented in AGENTS.md rule #25).
5. Surfaces a clean status report (`chrome running`, `daemon alive`,
   `skill registered`).

Subcommands: `start | stop | restart | status`.

Environment overrides: `BH_CHROME_BIN`, `BH_PORT` (default 9222),
`BH_PROFILE` (default `~/.config/chromium`).

## Browser-harness agent wiring

`config/agents/browser-harness.md` now prefers the Python tool:

```markdown
## Tools Available

- **Primary: `browser-harness` (Python via uv)** — installed at
  `~/.local/bin/browser-harness` from https://github.com/browser-use/browser-harness.
  Use heredoc syntax:
  ```bash
  browser-harness <<'PY'
  new_tab("https://example.com")
  wait_for_load()
  print(page_info())
  PY
  ```
  Pre-imported helpers: `new_tab`, `goto_url`, `page_info`,
  `click_at_xy`, `type_text`, `fill_input`, `press_key`, `scroll`,
  `capture_screenshot`, `list_tabs`, `current_tab`, `switch_tab`,
  `js`, `cdp`, `wait_for_load`, `ensure_real_tab`, `ensure_daemon`.
- **Fallback: `agent_browser_*` MCP tools** — only if the agent-browser
  MCP is connected. Prefer the primary.
```

And `config/opencode.json.template` now includes a registered
`browser-harness` agent entry under `agent:` so opencode can route
`--agent browser-harness` to it (previously it was a phantom agent
installed as a `.md` file but not registered).

### From opencode

The agent is registered in `~/.config/opencode/opencode.json`'s
`agent:` block. `opencode run --agent browser-harness` correctly
dispatches (no more "Falling back to default agent" warning). The
agent's bash tool can invoke `browser-harness` via heredoc as shown.

### The Arch Linux crashpad workaround

The system `/usr/bin/chromium` (Chromium 149) crashes on launch with:

```
[ERROR:third_party/crashpad/crashpad/util/file/filesystem_posix.cc:63]
mkdir /home/drb0rk/.config/chromium/Crash Reports/new:
Transport endpoint is not connected (107)
```

This is a known issue with crashpad on CachyOS / Arch. The fix is to
use `chrome-headless-shell` (from the puppeteer cache or from
`puppeteer-core`'s bundled binaries) which doesn't bundle crashpad.
`browser-harness-up.sh` automatically finds it.

## Edge cases

- **No chrome-headless-shell available**: `browser-harness-up.sh`
  falls back to system chromium. If that also fails (crashpad),
  the user sees a clear "install chromium or chrome-headless-shell"
  message.
- **Multiple Chrome instances**: the script refuses to start a second
  Chrome on the same port. If a stale one is found on the port, it
  must be stopped first (`bizar browser-harness-up stop`).
- **browser-harness daemon stuck**: `browser-harness --reload` kills
  the daemon so the next call picks up code changes.
- **Cloud browser billing**: documented in SKILL.md — don't leave
  `start_remote_daemon(...)` running without asking the user.

## Patterns surfaced

- **Thin CDP over a Python tool, not a sprawling MCP**: the 1k-LOC
  browser-harness Python package exposes more CDP primitives than the
  agent-browser MCP, with simpler reasoning (heredoc vs JSON tool
  calls). Where the agent can run a subprocess, prefer a thin CLI
  over an MCP wrapper.
- **Survive shell exit via `setsid + nohup + disown`**: chrome
  started with this pattern keeps running across `bash` tool timeouts
  in the opencode runtime. Without it, the user's "verify the app
  worked" agent session would lose Chrome mid-verification.
- **Skill via stdout**: `browser-harness skill > SKILL.md` registers
  the tool's full docs into the agent's skill loader. No scraping, no
  formatting; the tool emits exactly what agents should read.
