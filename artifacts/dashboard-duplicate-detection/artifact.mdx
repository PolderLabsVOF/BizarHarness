# Bug: Duplicate dashboard spawns linger forever

**Status:** `[STATUS:resolved]` · **Author:** `drb0rk` · **Created:** `2026-06-26T11:00:00.000Z`

> [DANGER]
> **Severity:** medium · Reported: 2026-06-26 · Reporter: drb0rk
>
> User-visible symptom: "there is one failed dashboard at port 4321,
> and one good one at 4322." Same machine, two dashboard processes,
> one healthy and one zombie. The port file only tracks the most
> recent start, so the old zombie stays around indefinitely.

## Summary

The Bizar dashboard can be left in a state where multiple node processes
are running on different ports, but only the most-recent one is recorded
in `~/.config/bizar/dashboard.pid` + `dashboard.port`. The un-recorded
ones become "orphans" — no way to stop them via `bizar dash stop`, no
way to know they exist via `bizar dash status`. They only surface when
the operator runs `netstat -tlnp` and notices two LISTEN rows.

## Reproduction

1. Start the dashboard in background on port 4321: `bizar dash start --bg`
2. The process listens on 4321 and writes its PID to `~/.config/bizar/dashboard.pid`.
3. Start it again on a different port: `bizar dash start --bg --port=4322`
4. Now port 4322 has the new dashboard (PID file updated). Port 4321
   still has the old one — but no one knows.
5. The old process is technically alive but, in the reported case, its
   HTTP handler was hung (TCP accepts, no response).
6. `bizar dash stop` only kills the PID from `dashboard.pid` (4322's
   process). Port 4321's process keeps running.

Confirmed locally: a 1h 43m-old dashboard at port 4321 (pid 835226)
running alongside the working 4322 one (pid 938619). Curl against 4321
returned no response — fully hung.

## Expected vs Actual

**Expected:** `bizar dash start` should refuse if another healthy
dashboard is already serving. The user should see a clear message
with the offending PIDs and an exit code. `bizar dash status` should
report every dashboard, not just the canonical one.

**Actual:** `bizar dash start` blindly allocates the next free port and
runs. Old dashboards pile up. `bizar dash status` only reports the
canonical (most recent) one.

## Root cause

The dashboard's lifecycle functions (`startDashboard`, `stopDashboard`,
`showStatus` in `bizar-dash/src/cli.mjs`) treat the `dashboard.pid` +
`dashboard.port` files as the single source of truth. They never scan
for sibling processes. Three things contribute:

1. **`findFreePort` accepts any free port.** If port 4321 has a hung
   process that occupies it but doesn't respond, `findFreePort(4321)`
   will skip to 4322 because 4321 is "in use" (LISTEN). No signal to
   the user that 4321 is hung.
2. **`stopDashboard` reads `dashboard.pid`** and SIGTERMs only that
   PID. Other dashboard processes are invisible to it.
3. **`status` reads `dashboard.port`** and prints the canonical URL.
   The dashboard can be serving on multiple ports simultaneously and
   `status` will never mention it.

## Fix

v3.20.7 introduces `bizar-dash/src/cli/dashboard-ports.mjs`, a discovery
helper that scans for every Bizar dashboard process and classifies each
as `healthy | zombie | orphan | dead`:

```js
import { findAllDashboards } from './cli/dashboard-ports.mjs';

const instances = await findAllDashboards();
// [
//   { pid: 938619, port: 4322, state: 'healthy', cmdline: '...' },
//   { pid: 835226, port: 4321, state: 'zombie',  cmdline: '...' },
// ]
```

Detection strategy:

1. Read the canonical PID from `dashboard.pid`.
2. Scan all `node` processes via `ps` for `bizar dash start` /
   `@polderlabs/bizar-dash/src/cli.mjs`.
3. For each candidate PID, walk `/proc/<pid>/fd` → socket inodes →
   `/proc/net/tcp` to find its listening port (Linux-only).
4. TCP-probe each candidate port (1.5s timeout, transport-only — no auth).
5. HTTP-probe each reachable port's `/api/health` endpoint.

Result classification:

- **healthy**: PID alive + `/api/health` returns `ok:true`
- **zombie**: PID alive + port accepts TCP but health probe fails (handler
  hung, event loop starved)
- **dead**: PID does not exist (orphaned port file)
- **orphan**: Port responds to health but no PID file claims it

### New CLI subcommand

```bash
bizar dash cleanup                    # kill zombies + dead PIDs
bizar dash cleanup --force            # also kill healthy non-canonical
bizar dash cleanup --kill             # SIGKILL instead of SIGTERM
```

`cleanup` never kills the canonical dashboard (the one matching
`dashboard.pid`). To stop the canonical one, use `bizar dash stop`.

### `start` now refuses duplicates

```bash
$ bizar dash start --bg
  ✗ Another Bizar dashboard is already running.

    pid 938619:4322  [healthy]  node ... bizar dash start --bg --port=4322

  To replace it, run `bizar dash cleanup` first, or pass
  --force to skip this check.
  To stop the canonical one, use `bizar dash stop`.
```

## Detection methods (notes)

- **`/proc/<pid>/fd` walk**: Linux-only. Skipped on macOS / Windows —
  the canonical PID file is the only signal there.
- **`ps -eo pid=,args=`**: portable. Greps argv for `bizar dash` /
  `@polderlabs/bizar-dash/src/cli.mjs`. Misses processes started via
  symlinks (rare).
- **`/proc/net/tcp`**: Linux-only. Parses `IP:PORT` and matches the
  inode of the PID's open sockets against the global socket table.
  Localhost (`127.0.0.1` = `0100007F`) and wildcard (`0.0.0.0` =
  `00000000`) only — we don't expose dashboards on public IPs by default.

## Edge cases handled

- **Port file but no PID**: the PID died but the file wasn't cleaned.
  Detected as `dead`. `cleanup` clears the stale files.
- **PID file with port file mismatch**: e.g. PID 1234 was on port 4321,
  then bumped to 4322 without overwriting the port file. The PID's
  listening port (via `/proc/net/tcp`) is authoritative; the port
  file is treated as a hint, not a constraint.
- **Multiple zombies**: `cleanup` sends SIGTERM to each, waits 1.5s,
  escalates any survivors to SIGKILL.
- **Orphan port without a known PID**: `cleanup` prints `lsof -i :PORT`
  hint; the user must kill the foreign process manually.
