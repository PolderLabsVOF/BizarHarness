# Dashboard: stale-PID-file false positive (recycled PIDs)

**Status:** `[STATUS:shipped]` · **Author:** `drb0rk` · **Created:** `2026-06-26T16:30:00.000Z`

> [INFO]
> v3.20.14 fixes the dashboard state machine so it can't get stuck on a
> phantom dashboard. The v3.20.13 lifecycle used `ps`-scan to detect other
> dashboards and `pidAlive(pid)` to confirm they're real. On a busy machine,
> Linux recycles PIDs in milliseconds — a `bizar dash start --bg` process at
> PID 938619 dies, gets reassigned to a chrome-headless-shell renderer, and
> the dashboard sees a "healthy" PID whose cmdline is
> `/path/to/chrome --type=renderer`. The `bizar dash start`/`stop`/`cleanup`
> cycle then becomes unrecoverable: `start` refuses ("Another dashboard is
> running"), `stop` says ("No dashboard running"), `cleanup --force` says
> ("Nothing to clean up").

## Problem

The bug surfaces as a three-way disagreement between `start`, `stop`, and `cleanup`:

```
$ bizar dash start --bg
  ✗ Another Bizar dashboard is already running.
    pid 938619:4322  [healthy]  node /home/drb0rk/.local/npm/bin/bizar dash start --bg --port=4322
  To replace it, run `bizar dash cleanup` first, or pass --force to skip this check.

$ bizar dash stop
No Bizar dashboard is running.

$ bizar dash cleanup
Found 1 dashboard:
     [healthy ] pid 938619   :4322      ps-scan
             node /home/drb0rk/.local/npm/bin/bizar dash start --bg --port=4322
Nothing to clean up. Use --force to also kill healthy non-canonical duplicates.
```

Three commands disagreeing is the canonical symptom of a state machine that
trusts `pidAlive(pid)` to mean "this process is what I think it is".

### Root cause

Two interlocking bugs:

1. **`pidAlive` returns true for recycled PIDs.** Linux reuses PIDs in
   milliseconds. `process.kill(pid, 0)` succeeds when `pid` belongs to a
   brand-new unrelated process. There is no portable way to ask the kernel
   "is this the same process I saw earlier" — by the time you ask, the PID
   may have been reassigned.

2. **The dashboard lifecycle trusts `pidAlive` + `ps`'s argv to confirm
   identity.** `psScanDashboards` ran `ps -eo pid=,args= | grep -E
   '(bizar dash|@polderlabs/bizar-dash/src/cli.mjs)'`. The cmdline was
   *current* when `ps` ran (it re-reads /proc each call), but the dashboard
   cached the PID and trusted it for subsequent decisions — across the
   `pidAlive`, `pidListeningPort`, and `httpHealth` probes.

The two bugs combine: `ps` returns a real-looking PID whose cmdline is
whatever the recycled owner runs, `pidAlive` says alive, and the dashboard
sees a healthy phantom.

### Prior attempts that didn't fix it

- **v3.20.7** added `findAllDashboards()` with ps-scan + canonical PID
  file + port scan + health probe. Helped with the "zombie dashboard"
  problem but not the recycled-PID problem.
- **v3.20.13** added `cleanup` for non-canonical duplicates. Required
  `--force` even when the canonical PID was dead, which left orphaned
  dashboards running.

## Goals

- [x] Reject processes whose cmdline doesn't structurally look like a Bizar
      dashboard launch (chrome renderers, ssh sessions, shell commands
      whose body mentions "bizar dash" in a comment)
- [x] Re-verify the cmdline at probe time, not just at scan time, to
      catch the recycled-PID race
- [x] Mark the canonical PID-file entry as `dead` (not `canonical`) when
      the PID has been recycled to an unrelated process
- [x] `bizar dash stop` kills every healthy/zombie dashboard found, not
      just the one in the canonical PID file
- [x] `bizar dash cleanup` kills healthy non-canonical orphans when the
      canonical PID is dead/recycled (no more `--force` needed)
- [x] `bizar dash status` reports every healthy dashboard, not just the
      canonical PID file's entry
- [x] Cover with regression tests in
      `bizar-dash/tests/dashboard-ports.test.mjs`

## Non-goals

- **Detecting the recycle race in real time.** The best we can do is
  re-verify the cmdline at every decision point; between those points,
  the kernel may still recycle the PID. The window is small (sub-ms in
  most cases) and the worst-case outcome is the previous bug.
- **Cross-platform PID-validity guarantees.** `pidAlive` is unreliable
  on every POSIX system; the structural cmdline check is what actually
  protects us.
- **Locking the dashboard's port.** A second dashboard could still
  race-start during the `findAllDashboards()` window. The 4321-4530 port
  range scan catches orphans after the fact.

## Design

The fix has three parts: structural cmdline check at scan time,
re-verification at probe time, and stale-aware canonical classification.

### Structural cmdline check

```js
function cmdlineLooksLikeDashboard(cmdline) {
  if (!cmdline || typeof cmdline !== 'string') return false;
  // Direct CLI invocation
  if (/\/@polderlabs\/bizar-dash\/src\/cli\.mjs\b/.test(cmdline)) return true;
  // Wrapped via the `bizar` bin: <path>/bizar dash <subcommand>
  if (/(?:^|[\/\\])\S*bizar\s+dash\s+(?:start|tui|stop|status|cleanup)\b/.test(cmdline)) return true;
  return false;
}
```

The two key constraints that catch false positives:

1. **`/@polderlabs/bizar-dash/src/cli.mjs\b`** — exact path match (basename
   anchored to the package path). Rejects `<some-tool> --cli.mjs`,
   `my-bizar-dash-config`, etc.

2. **`(?:^|[\/\\])\S*bizar\s+dash\s+(?:start|tui|...)\b`** — the `bizar`
   token must be preceded by a path separator or start-of-string. Rejects
   `bash -c "echo I want to run bizar dash start"` (the `bizar` is mid-string
   inside a quoted argument) and `man bizar-dash-config` (no `dash` argv).

### Probe-time re-verification

```js
function verifyCmdlineAtProbeTime(pid) {
  if (!pid) return null;
  try {
    const cmdline = readFileSync(`/proc/${pid}/cmdline`, 'utf8').replace(/\0/g, ' ').trim();
    if (cmdlineLooksLikeDashboard(cmdline)) return cmdline;
    return null;  // PID recycled to a different process
  } catch {
    return null;  // PID dead
  }
}
```

`findAllDashboards()` re-applies this check inside the probe loop
**after** `pidAlive()` succeeds. The window between `pidAlive` and
the cmdline re-read is still a race, but it's sub-millisecond and the
worst-case outcome is the previous bug — not silent data loss.

### Stale-aware canonical classification

```js
const cmdlineMatches = cmdlineLooksLikeDashboard(cmdline);
byPid.set(canonical.pid, {
  pid: canonical.pid,
  state: alive && cmdlineMatches ? 'unknown' : 'dead',
  isCanonical: cmdlineMatches,  // ← was always true
  ...
});
```

Previously, the canonical PID-file entry was always `isCanonical: true`.
That meant a recycled PID would be marked "canonical" even though it no
longer belongs to the dashboard. The cleanup logic relies on
`isCanonical` to decide whether to preserve a dashboard — so a recycled
canonical would block cleanup of real orphans.

### Stale-file cleanup

`stopDashboard()` now uses `findAllDashboards()` and clears the canonical
PID/port files when they're stale (no live dashboard found):

```js
async function stopDashboard() {
  const instances = await findAllDashboards();
  const alive = instances.filter((i) => (i.state === 'healthy' || i.state === 'zombie') && i.pid);
  if (alive.length === 0) {
    if (existsSync(PID_FILE)) {
      console.log(`Stale PID file at ${PID_FILE} — clearing.`);
      unlinkSync(PID_FILE);
    }
    // ...
    return;
  }
  for (const inst of alive) {
    process.kill(inst.pid, 'SIGTERM');
  }
  // ... wait + SIGKILL escalation ...
}
```

## Pattern

**Never trust `pidAlive(pid)` as identity.** On Linux, PIDs are recycled
in milliseconds. A successful `process.kill(pid, 0)` only tells you the
PID number is in use — not that it's still the same process. For state
machines that need to track "is process X still running?", always pair
the liveness check with an identity check (cmdline, executable path,
parent PID, etc.) and re-apply the identity check at every decision
point, not just at scan time.

The "sub-ms race" between `pidAlive` and `cmdline read` is acceptable
because the worst-case outcome is the same as before — not a silent
data corruption. State machines that care about atomicity need a
stronger mechanism (file lock, advisory lock, IPC handshake).
