# Decision: Vidarr uses MiniMax M3 (drop GPT-5.5 / Anthropic fallback)

**Status:** `[STATUS:accepted]` · **Author:** `drb0rk` · **Date:** `2026-06-26`

> [INFO]
> This ADR captures the decision to point the `vidarr` agent (the
> last-resort Tier 5 subagent) at `minimax/MiniMax-M3` instead of
> `openai/gpt-5.5`, and to remove the `ANTHROPIC_API_KEY` requirement
> from the install flow. Drives from the user's repeated observation
> that "it should just be MiniMax and opencode-zen".

## Context

The Bizar agent system uses a 5-tier model routing architecture. Two
classes of providers are available:

| Tier | Provider | Models | Auth |
|------|----------|--------|------|
| Free | `opencode/deepseek-v4-flash-free` (OpenCode Zen) | DeepSeek V4 Flash | No API key |
| Paid | `minimax/MiniMax-M3`, `minimax/MiniMax-M2.7` | MiniMax Anthropic-format API | `MINIMAX_API_KEY` env var |

Pre-v3.20.7, the `vidarr` agent (last-resort Tier 5) was configured with
`model: openai/gpt-5.5` and required `OPENAI_API_KEY` at install time
(prompts.mjs explicitly asked for it). This produced two real problems:

1. **Operator experience**: the dashboard log filled with
   `Anthropic API key is missing` whenever vidarr was dispatched,
   because opencode falls back to ANTHROPIC_API_KEY for any model that
   doesn't have a key on file. The error was misleading (the user
   had no Anthropic account and didn't want one).
2. **Provider drift**: the documented model stack is MiniMax + opencode-zen.
   The vidarr gpt-5.5 entry violated the documented contract.

The user explicitly stated: "i got some error about antropic key not found.
it should just be minimax and opencode zen."

## Options considered

### Option A: Keep GPT-5.5 + require `OPENAI_API_KEY`

- Pros: GPT-5.5 is genuinely stronger on hard reasoning benchmarks.
- Cons: Adds a third required provider to the install. The user's
  stated setup (MiniMax + opencode-zen) doesn't include OpenAI.
  Every vidarr invocation fails until they sign up for OpenAI.

### Option B: Switch to `minimax/MiniMax-M3`

- Pros: Uses the existing provider. Same model tier as Tyr (the next-strongest
  agent). Reasoning-enabled with interleaved thinking. No new keys needed
  for users who already have `MINIMAX_API_KEY`.
- Cons: Marginally weaker on the very hardest problems (no GPT-5.5 benchmark
  data available; per the user's preference, this is acceptable).

### Option C: Drop vidarr entirely; fall back to Tyr

- Pros: One less agent to maintain.
- Cons: Loses the explicit "last resort" tier with plan-then-Forseti
  gating. Tyr's reasoning budget isn't meaningfully different from M3-MiniMax.

## Decision

We chose **Option B**. Vidarr now uses the same model as Tyr (MiniMax M3)
but retains its own system prompt focused on postmortem and last-resort
reasoning. The cost ceiling is identical to Tyr; the differentiator is
the prompt (cross-tier thinking) and the gated invocation path (only when
Tyr has demonstrably stalled).

This also lets us:

1. Remove the `OPENAI_API_KEY` prompt from `cli/prompts.mjs` install.
2. Remove `openai/gpt-5.5` from `cli/audit.mjs` `validModels` whitelist.
3. Update the install banner in `install.sh` and the AGENTS.md routing
   table to reflect MiniMax-only.

## Consequences

### Positive

- Install flow now asks for exactly two keys: `MINIMAX_API_KEY` (for paid
  MiniMax models) and an Obsidian vault path. No more "what's an OpenAI
  key for?" confusion.
- The misleading `Anthropic API key missing` error from opencode is gone
  for vidarr-spawned sessions.
- Audit (`bizar audit`) now correctly flags any future drift back to
  `openai/gpt-5.5` or other non-MiniMax/opencode-zen models.
- One less provider config block to maintain.

### Negative

- The absolute ceiling on Bizar reasoning drops from "GPT-5.5" to
  "MiniMax M3". If a problem truly requires GPT-5.5-class reasoning,
  the user must drop down to raw opencode and dispatch it directly.
- We have no empirical data on how often vidarr's "stuck after Tyr"
  cases would have benefited from GPT-5.5. The decision is based on
  operator preference, not benchmarks.

### Mitigations

- If the user later wants Tier 5+ reasoning, we can add an opt-in
  override via `BIZAR_VIDARR_MODEL_OVERRIDE` env var.
- Forseti (also MiniMax M3) continues to audit all Tier 4/5 plans
  before they ship, which keeps the reasoning quality bar high
  regardless of which model runs the actual work.

## Supersedes

- The implicit assumption in pre-v3.20.7 docs and prompts that the
  Bizar system could fall back to a third-party model provider
  beyond MiniMax and opencode-zen.
