# Release Notes — `@polderlabs/bizar@4.0.0`

**Date:** 2026-06-29
**Tag:** `v4.0.0`
**Status:** BREAKING — restructured package layout

## TL;DR

`@polderlabs/bizar` is now a single npm package. The dashboard server (`@polderlabs/bizar-dash`), the opencode plugin (`@polderlabs/bizar-plugin`), and the typed SDK (`@polderlabs/bizar-sdk`) are no longer separately published — they ship as sub-directories of the unified root package. One install, one `node_modules/`, one lockfile.

This is a major version bump because the package layout changed. Existing v3 users only need to upgrade their install command (`npm install -g @polderlabs/bizar@latest`) — every component is still bundled.

## What changed

- **One package instead of four.** `@polderlabs/bizar` now includes the dashboard server, the opencode plugin, and the typed SDK.
- **No more separate publishes.** `@polderlabs/bizar-dash`, `@polderlabs/bizar-plugin`, and `@polderlabs/bizar-sdk` are removed from the npm registry as standalone packages.
- **Sub-directories stay.** `bizar-dash/`, `plugins/bizar/`, and `packages/sdk/` remain in the repo as sub-directories of the unified package. The source layout is unchanged — only the npm package boundaries moved.
- **`workspaces` removed.** Root `package.json` no longer declares `"workspaces": ["packages/*"]`. The SDK is built with a direct `tsc -p packages/sdk/tsconfig.json` invocation.
- **Single `node_modules/`.** Root `node_modules/` is now the single install target. The plugin's `node_modules/` is no longer bundled on deploy (the SDK is part of the same package now).
- **`engines` declaration added.** `engines: { "node": ">=18", "bun": ">=1.1.0" }` declares bun as a runtime requirement (needed for plugin tests).
- **`allowScripts` declaration added.** `better-sqlite3@12.11.1` is explicitly allow-listed so npm does not skip its native build step.
- **Memory Service (Phase 1) ships.** The new `bizar memory <sub>` family, dashboard `/api/memory/*` routes, schema validator, secret scanner, and Git-backed sync (released in v3.24.0) are part of v4.0.0.

## Migration

### For existing v3 users

```bash
npm install -g @polderlabs/bizar@latest
```

That's it. The dashboard, plugin, and SDK are all bundled in the new package. No separate `npm install -g @polderlabs/bizar-dash` step is needed (and it would no-op anyway — the dashboard is no longer published as a standalone package).

### For contributors (source layout)

If you have a `git clone` checkout:

1. `git pull` to fetch the v4.0.0 tag.
2. `rm -rf node_modules` (if you previously had workspaces installed).
3. `npm install` from the repo root to regenerate the lockfile and `node_modules/`.
4. Re-run `./install.sh` to refresh `~/.config/opencode/plugins/bizar/` and `~/.config/opencode/opencode.json`.

### For internal imports

Imports between the four former packages now use relative paths. The plugin imports the SDK via `./packages/sdk/src/index.js` style paths instead of `@polderlabs/bizar-sdk`. The dashboard server's internal imports were also rewritten.

## File map (old → new)

| Old (v3) | New (v4) |
|---|---|
| `bizar-dash/package.json` (`@polderlabs/bizar-dash`) | `package.json` (deps merged into root) |
| `plugins/bizar/package.json` (`@polderlabs/bizar-plugin`) | `package.json` (deps merged into root) |
| `packages/sdk/package.json` (`@polderlabs/bizar-sdk`) | `package.json` (deps merged into root) |
| `workspaces: ["packages/*"]` in root | (removed) |
| `node_modules/@polderlabs/bizar-sdk` (symlink) | `packages/sdk/` (consumed as relative import) |
| `node_modules/@polderlabs/bizar-dash/` (post-install copy) | (no longer needed; SDK ships inside the same package) |
| `install.sh` npm-installs 2 packages | `install.sh` installs 1 package |
| `install.sh` copies plugin's bundled `node_modules/` | (removed — SDK is internal) |
| `install-state.json` tracks `bizar-dash` version | `install-state.json` only tracks `bizar` version |

## Test counts

- **Plugin tests** (`bun test`): 13 test files covering loop detection, block reasoning, stall detection, background delegation, plan actions, command dispatch, key rotation, and reasoning cleanup.
- **SDK tests** (`vitest run`): SDK contract tests for HTTP + SSE protocol types.
- **Dashboard tests** (`node --test`): 18 test files covering YAML parser, memory store, schema, secrets, Git ops, sync, back-compat, mod lifecycle, dashboard ports, and submit-feedback.
- **Total**: 85 new tests in v3.24.0 (Memory Service Phase 1), all passing. v4.0.0 itself adds no new tests — the restructure is mechanical.

## Notes for contributors

### Bun requirement

Plugin tests use `bun test`. The new `engines` declaration makes this an explicit requirement:

```bash
# Install bun (one-time)
curl -fsSL https://bun.sh/install | bash

# Run plugin tests
bun test plugins/bizar/tests/loop.test.ts
```

Node alone cannot execute the plugin tests — they depend on Bun's `bun:test` API and Bun-specific module resolution.

### Lockfile regeneration

After editing the consolidated root `package.json`, regenerate the lockfile from the repo root:

```bash
rm -f package-lock.json
npm install --package-lock-only
```

The lockfile is gitignored (`.gitignore` line 2), so it is not committed. Each developer regenerates it locally.

### Building the SDK

The SDK is built with a direct `tsc` invocation:

```bash
npm run build:sdk         # tsc -p packages/sdk/tsconfig.json
```

Or run the SDK tests directly:

```bash
npm run test:sdk          # vitest run, via packages/sdk/package.json
```

### `package.json` scripts

The root `package.json#scripts.test` now runs every test suite in one command:

```bash
npm test                  # typecheck + SDK tests + bun plugin tests + node dashboard tests
```

This replaces the old workspace-scoped commands (`npm run test -w @polderlabs/bizar-sdk`) which no longer work without workspaces.

## What's next

v4.0.0 is a structural release — no new features. The Memory Service Phase 1 (already shipped in v3.24.0) is the headline feature; v4.0.0 just consolidates the package layout to make the codebase easier to install and contribute to.

Phase 2 of the Memory Service (wire the `mods-examples/lightrag/` server as the derived retrieval index) will be the next major addition.
